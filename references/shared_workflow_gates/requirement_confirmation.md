# Requirement Confirmation

通用需求确认门禁：

1. 需求分析结束后，不允许默认直接切到 UI设计师或交付阶段
2. 只有当 `用户确认状态 = 允许进入下一阶段` 时，才允许进入 UI 设计或交付
3. 只要缺口会影响页面形态、信息架构、内容来源、主 CTA、核心交互或关键边界态，就必须先问用户
4. 需求分析输出必须先形成 `Design Task Brief`，至少包含：
   - 任务目标
   - 页面范围
   - 目标平台
   - 主 CTA / 主任务路径
   - 关键交互与关键状态
   - 非目标 / 不做范围
   - 验收标准
   - 约束
   - `auto_assumption`（如有）
5. Brief 中凡未确认项，必须显式标注 `候选（未确认）`
6. 没有拿到回答前，不要输出完整方案，不要切下一个阶段
7. 用户只回复“确认 / 可以 / 按这个来 / 没问题”时，只能确认上一轮明确摘要中的条目
8. 如果仍有摘要外的未决项，必须先回写“已确认 / 待确认”，不能把一句确认扩展成全部通过
9. 如果确认后发现原 brief 与现有输入、截图、文件事实冲突，必须回退到需求确认阶段，不能带着冲突继续推进

提问预算补充：

- `L1`：0-2 问，通常不进入完整确认门禁
- `L2`：2-4 问，确认项只保留会改变页面结构或交互的内容
- `L3`：4-7 问，允许覆盖流程、异常、边界和重设计判断
- `L4`：6-10 问，但必须分阶段确认，不一次问完

确认门禁追求的是“够用收口”，不是“问题越多越安全”。

禁止行为：

- 把推荐方案当成用户确认
- 因为提问预算已用完而强行收口
- 因为任务看起来简单而跳过 brief
- 需求未闭环就切到 UI设计师
